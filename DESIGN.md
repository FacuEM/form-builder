## Problem Statement

A web application for building and filling forms, inspired by Typeform's one-question-per-page UX. Two distinct audiences:

1. **Creators** — build forms by composing questions with typed answer fields (short text, long text, multiple choice, dropdown). Manage and view responses.
2. **Respondents** — fill out a published form via a public URL. One question per page. Must answer the current question to advance. Cannot skip.

The defining characteristic is craft: minimalistic, fully dark aesthetic, smooth directional animations between questions. This is what makes it different from the open-source alternatives that all compete on feature count rather than feel.

---

## What Makes This Cool

- **Directional `AnimatePresence` slide** — questions slide in from the right going forward, from the left going back. Fixed duration (not spring), ~440ms total. This single interaction, done correctly, signals "built with intent."
- **Keyboard-first respondent UX** — A/B/C/D key shortcuts for choices, Enter to advance, arrow keys for back/forward. Feels native, not web-y.
- **Mobile-adaptive UX** — "Tap to continue" button on touch devices. No iOS Safari back-gesture conflict. Continue button is always visible on mobile.
- **"Press Enter ↵" affordance** — fades in 800ms after a question appears on desktop. Shows a Continue button on touch devices.
- **Thin progress bar** — 2px at the top of the respondent view, animates width. No percentage numbers, no step counters. Ambient progress.
- **Fully dark across all surfaces** — builder, respondent view, and dashboard are all #080808–#0d0d0d. No light/dark split.

- Next.js App Router, TypeScript, Tailwind CSS — no heavy component library
- Framer Motion for all animations — first-class, not cosmetic
- Custom Tailwind components throughout — copy component source from shadcn/ui where useful (e.g., Dialog, Popover), strip all default styles, apply project dark tokens

## Premises

1. **Two separate routes** — builder (`/dashboard/forms/[id]/edit`) and respondent (`/forms/[id]`) are distinct pages. No side-by-side preview mode at launch.
2. **Framer Motion is first-class** — the animation library is chosen from day one and informs component structure, not added later.
3. **Full storage scope** — auth + database + dashboard = ~40% of total build scope.
4. **Custom components** — no shadcn default aesthetic. Tailwind tokens + custom primitives.
5. **Vercel deploy** — forms shared via `/forms/[id]`. No self-hosting requirement.

## Routes & Architecture

All `/dashboard/*` routes are protected by Next.js middleware (`middleware.ts`). Unauthenticated requests redirect to `/login`. `/forms/[id]` is fully public — no auth required for respondents. If `Form.published === false`, the respondent route returns a 404 via Next.js `notFound()`.

**Auth:** Supabase Auth via `@supabase/ssr`. **Database:** Supabase Postgres + Prisma ORM. **API layer:** Use Server Actions for builder mutations (create question, reorder, update settings). Use Route Handlers for the public response submission endpoint (`POST /api/forms/[id]/responses`) because it must be callable from a client component without React context.

**Supabase + Prisma connection:** Use Supabase's Session Mode connection string (port 5432) for Prisma. Set `DATABASE_URL` to the session-mode URL and `DIRECT_URL` to the direct connection string. Add `directUrl` to `datasource db` in `schema.prisma` — required to avoid PgBouncer timeout errors in serverless.

**Security:** RLS disabled on all tables. Prisma + `SUPABASE_SERVICE_ROLE_KEY` is the sole access control layer. `SUPABASE_SERVICE_ROLE_KEY` is server-only — used only in `lib/supabase/server.ts`, never exported to client components, never prefixed `NEXT_PUBLIC_`. Every creator-scoped Prisma query must include a `creatorId` filter — this is the only ownership check, enforced in code.

## Data Model

```prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")      // Session Mode, port 5432
  directUrl = env("DIRECT_URL")        // Direct connection (avoids PgBouncer for migrations)
}

generator client {
  provider = "prisma-client-js"
}

model Form {
  id               String     @id @default(cuid())
  title            String
  creatorId        String                               // populated from supabase.auth.getUser() in Server Actions
  published        Boolean    @default(false)
  thankYouMessage  String     @default("Thanks for your response.")
  questions        Question[]
  responses        Response[]
  createdAt        DateTime   @default(now())
  @@index([creatorId])                                  // dashboard list query: WHERE creatorId = ?
}

model Question {
  id          String       @id @default(cuid())
  formId      String
  order       Int
  text        String
  type        QuestionType  // TEXT | LONG_TEXT | CHOICE | DROPDOWN
  required    Boolean      @default(true)
  choices     Choice[]
  answers     Answer[]
  form        Form         @relation(fields: [formId], references: [id], onDelete: Cascade)
}

model Choice {
  id         String   @id @default(cuid())
  questionId String
  label      String
  order      Int
  question   Question @relation(fields: [questionId], references: [id], onDelete: Cascade)
}

model Response {
  id              String   @id @default(cuid())
  formId          String
  respondentToken String?  // client-generated UUID (crypto.randomUUID()); nullable for private browsing
  answers         Answer[]
  createdAt       DateTime @default(now())
  completed       Boolean  @default(false)
  form            Form     @relation(fields: [formId], references: [id], onDelete: Cascade)
  @@unique([respondentToken, formId])                   // enables Prisma upsert for idempotent first POST (NULL tokens don't participate in uniqueness in Postgres)
  @@index([formId])                                     // responses list query
  @@index([createdAt])                                  // dashboard sort
}
// respondentToken lifecycle:
//   - Client generates crypto.randomUUID() before first POST, stores in localStorage["respondent_token"]
//   - Sent in every POST; server upserts Response on (respondentToken, formId)
//   - If localStorage unavailable (private browsing, SSR): submit without token — Response created fresh each time
//   - Used for future deduplication only; V1 dashboard shows one row per Response record

model Answer {
  id         String @id @default(cuid())
  responseId String
  questionId String
  value      String  // stores choice LABEL text at submission time (snapshot semantics)
                     // NOT the Choice.id — self-contained, survives choice edits/deletions
  response   Response  @relation(fields: [responseId], references: [id], onDelete: Cascade)
  question   Question  @relation(fields: [questionId], references: [id], onDelete: Cascade)
  @@unique([responseId, questionId])                    // enables Prisma upsert for re-answers
}

enum QuestionType {
  TEXT
  LONG_TEXT
  CHOICE
  DROPDOWN
}
```

## Animation Spec

| Interaction | Implementation |
|---|---|
| Question transition (forward) | `AnimatePresence` + slide from `x: 60` to `x: 0`, exit to `x: -60` |
| Question transition (back) | `AnimatePresence` + slide from `x: -60` to `x: 0`, exit to `x: 60` |
| Question transition config | `ease: [0.25, 0.1, 0.25, 1], duration: 0.22` — fixed, not spring. Exit 220ms + enter 220ms = ~440ms total with `mode="wait"`. |
| Progress bar | `motion.div` with `animate={{ width: "X%" }}`, spring `stiffness: 300, damping: 30` |
| NavigationHint (desktop) | `animate={{ opacity: 1 }}` after 800ms delay. Shows "Press Enter ↵". `useEffect` with `clearTimeout` on unmount. |
| NavigationHint (mobile/touch) | Always-visible "Continue →" button that calls `navigate('forward')`. Hidden on desktop (pointer: fine). |
| Choice selection | 150ms ease-out border-color + background on `selected` state |
| Dropdown auto-advance | `useEffect` wrapping 300ms `setTimeout`, `clearTimeout` returned on unmount |

Direction detection: `useRespondentState` (not `useFormState` — that is a reserved React/Next.js name) — full interface:
```ts
{
  currentIndex: number,
  direction: 'forward' | 'back',
  answers: Record<string, string>,
  navigate: (dir: 'forward' | 'back') => void,
  setAnswer: (questionId: string, value: string) => void,
  submitting: boolean,     // true while POST is in-flight; question components disable Enter/Continue while true
}
```

**Race condition fix:** Freeze `direction` in a `ref` at the moment of navigation. Do not read from state inside the exit variant — state may have updated before the exit animation completes.

**`AnimatePresence` config:** Use `<AnimatePresence mode="wait">` so the exit animation completes before the enter animation begins.

**Timing decision — fixed duration, not spring, for `QuestionSlide`:** `mode="wait"` serializes exit + enter; spring produces 600–800ms total — too slow. Use `ease: [0.25, 0.1, 0.25, 1], duration: 0.22`.

`QuestionSlide` variant map:
```ts
const variants = {
  enter:  (dir: 'forward' | 'back') => ({ x: dir === 'forward' ? 60 : -60, opacity: 0 }),
  center: { x: 0, opacity: 1 },
  exit:   (dir: 'forward' | 'back') => ({ x: dir === 'forward' ? -60 : 60, opacity: 0 }),
}
// Key prop on the motion.div must be the question ID to trigger AnimatePresence re-mount.
```

**Required field validation:** If a required question has an empty answer and the user presses Enter (or taps Continue), show inline shake on the input. Use `motion.div` with `animate={{ x: [0, -8, 8, -8, 0] }}`, duration 0.3s. Do not advance.

**On submission error:** Show inline error below the current answer input. Do not navigate. Error dismisses on retry.

## Mobile UX

On touch devices (detect via `window.matchMedia('(pointer: coarse)')` or `'ontouchstart' in window`):

- **Navigation:** Replace "Press Enter ↵" hint with a visible "Continue →" button. No swipe gestures — avoid iOS Safari edge-swipe conflict.
- **TextQuestion:** `<input>` renders normally; `<textarea>` for LONG_TEXT auto-grows.
- **ChoiceQuestion:** Keyboard shortcuts (A/B/C/D) disabled on touch. Tap to select, then tap Continue button.
- **DropdownQuestion:** Native `<select>` picker. Auto-advances after 300ms on `onChange` — unchanged on mobile.
- **NavigationHint:** Conditionally renders "Press Enter ↵" on `pointer: fine`, "Continue →" button on `pointer: coarse`.

## QuestionEditor Spec

`QuestionEditor.tsx` receives the selected `Question` and a set of Server Action callbacks. Component states:

1. **Question text** — `<textarea>` (auto-grow) bound to `question.text`. Saves on `blur` via `updateQuestion` Server Action + `revalidatePath`.
2. **Type picker** — segmented control: TEXT / LONG TEXT / CHOICE / DROPDOWN. Changing type calls `updateQuestionType` Server Action.
   - **Type-switch behavior:** Switching TO `TEXT` or `LONG_TEXT` when choices exist: show inline warning "Switching type will remove existing choices." One confirm click to proceed.
   - Switching FROM text TO `CHOICE`/`DROPDOWN`: shows empty choices list, no warning needed.
3. **Choices list** (visible only when type is `CHOICE` or `DROPDOWN`):
   - Each choice has an inline text input bound to `choice.label`, saves on `blur`.
   - Trash icon removes the choice (calls `deleteChoice` Server Action).
   - "Add option" button at the bottom appends a new empty Choice.
   - Choices sorted by `choice.order`; order maintained by up/down buttons (matching QuestionList pattern).
4. **Required toggle** — maps to `question.required`. Updates via Server Action.

Each Server Action in the builder must call `revalidatePath('/dashboard/forms/[id]/edit')` after mutating — otherwise the UI won't reflect changes until a hard refresh.

## Server Action Auth Pattern

Every builder Server Action must get the authenticated user's ID. Pattern:

```ts
// app/actions/form.ts
import { cookies } from 'next/headers'
import { createServerClient } from '@/lib/supabase/server'
import { prisma } from '@/lib/db'

export async function createForm(title: string) {
  const supabase = createServerClient(cookies())
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) throw new Error('Unauthorized')

  return prisma.form.create({
    data: { title, creatorId: user.id, published: false }
  })
  // Always revalidate after mutations:
  revalidatePath('/dashboard')
}
```

Every creator-scoped query must filter by `creatorId: user.id` — this is the sole ownership check (RLS is disabled).

## Partial Response Save Strategy

**API contract — per-question writes:**

Each time the respondent advances past a question, `FormPlayer` fires `POST /api/forms/[id]/responses`:

```ts
// First question answered: creates/finds Response + first Answer
{ respondentToken: string, answers: [{ questionId: string, value: string }] }
// → server upserts Response on (respondentToken, formId) [@@unique constraint]
// → creates Answer row
// → returns { responseId }

// Subsequent questions: adds Answer to existing Response
{ responseId: string, respondentToken: string, answers: [{ questionId: string, value: string }] }
// → upserts Answer on (responseId, questionId) [@@unique constraint]
```

**Answer value:** For `CHOICE` and `DROPDOWN` types, store `Choice.label` text at submission time (snapshot semantics). Not the ID. This survives choice edits and deletions.

**Idempotency:** `respondentToken` is generated by the client via `crypto.randomUUID()` before the first POST and stored in `localStorage["respondent_token"]`. The server upserts on `(respondentToken, formId)` — safe to retry on network failure.

**Guards in POST handler:**
1. Fetch form by `formId` — 404 if not found
2. Check `form.published === true` — 403 if false
3. Upsert Response, upsert Answer

`FormPlayer` holds `responseId: string | null` in local state (null until first successful POST). Subsequent calls include `responseId` only when non-null.

`Response.completed` is set to `true` on the final answer (`questionIndex === totalQuestions - 1`). Partial responses (`completed: false`) stay in the DB — creator can see them in the dashboard.

## Edit-After-Publish Policy

Creators can edit a published form that has responses. The builder shows a warning banner when the form has `Response` rows:

> "This form has responses. Editing or deleting questions may affect how existing responses display."

**Orphan policy:** If a Question is deleted, its associated `Answer` rows remain in the DB (cascade is on the Question→Answer relation with `onDelete: Cascade` actually removing them — but the Response rows stay). The responses dashboard must handle questions that no longer exist: skip `Answer` rows where `questionId` has no matching `Question` (filter at the query layer).

Actually — with `onDelete: Cascade` on `Answer`, deleting a `Question` WILL delete its `Answer` rows. This is the correct behavior for V1: historical answers for deleted questions are removed. The warning banner is still appropriate.

## Responses Dashboard Spec

`/dashboard/forms/[id]/responses` shows:
- **Table columns:** submission time, completion status (complete / partial), per-question answer preview (truncated to 40 chars)
- **Row click:** opens `ResponseDetail.tsx` slide-over panel on the right — all questions and answers for that respondent
- **Query:** `prisma.response.findMany({ where: { formId }, include: { answers: true }, orderBy: { createdAt: 'desc' } })` — one query, no N+1
- **Questions fetched separately:** `prisma.question.findMany({ where: { formId }, orderBy: { order: 'asc' } })` — used to render column headers and match answers
- **No CSV export in V1**
- **No filters or search in V1**
- All responses are anonymous; `respondentToken` never displayed to the creator.

## Closed Decisions

1. **Auth:** Supabase Auth (`@supabase/ssr`)
2. **Database:** Supabase Postgres + Prisma ORM. RLS disabled, Prisma owns access control.
3. **Drag-to-reorder:** Deferred. V1 uses up/down arrow buttons in `QuestionList.tsx` and `QuestionEditor.tsx`. V2 adds `@dnd-kit/sortable`.
4. **Form end state:** `ThankYouScreen.tsx` ships in V1. Default: "Thanks for your response."
5. **respondentToken:** Client-generated `crypto.randomUUID()` before first POST. Stored in `localStorage["respondent_token"]`. Nullable (private browsing).
6. **Answer.value type:** Stores choice label text at submission time (snapshot semantics). Not Choice.id.
7. **Edit-after-publish:** Allowed with warning banner. Orphan policy: deleting a question cascades to delete its Answer rows (with warning shown to creator).
8. **Mobile UX:** Continue button always visible on touch devices. No swipe navigation. iOS Safari safe.
9. **Rate limiting:** V2 TODO — Vercel WAF / edge rate limit on `POST /api/forms/[id]/responses`. Not in V1.
